# ESP32-4848S040 physical board and display consumer

The part kind is `esp32_4848s040`; the firmware device id is
`esp32-4848s040`. The generic ESP32-S3 target (`esp32s3`) remains separate.
This face describes the common GUITION C_I display/touch board with 16 MB
flash and 8 MB octal PSRAM. Optional relay, audio and SD assemblies do not
gain simulated behavior by placing it.

## Physical connections

The drawing is original bw-parts art, combining a front display with a
clearly labelled rear H1 connector inset. Its `240 × 160` view box is a
stylised layout, not a mechanical scale. It has no breadboard footprint.
The same transform places the art, wire terminals, hit box and display
aperture. Only these eight physical H1 terminals are exposed:

| Rear H1 row | Left terminal | Right terminal |
|---|---|---|
| 1 | `gnd` | `gnd2` |
| 2 | `gpio40` | `gpio44` (UART0 RX) |
| 3 | `gpio2` | `gpio43` (UART0 TX) |
| 4 | `gpio1` | `5v` |

GPIO uses 3.3 V logic. `5v` feeds the board regulator and must not feed a
GPIO. There is no H1 3.3 V output. Automatic wiring uses a separate 3.3 V
signal supply and a 5 V board supply with common ground. Button wiring uses
an explicit 10 kΩ pull-up to 3.3 V. GPIO1 and GPIO2 are the exposed ADC pins.
Internal LCD/touch/memory signals and GPIO22–25 cannot become connections,
even if an imported file supplies a larger terminal list. Imported stale
wires naming those pins produce a design-rule finding. The voltage check
distinguishes a 3.3 V source from 5 V instead of treating every VCC symbol
as a 5 V source.

GPIO40/2/1 can be shared with optional relay or audio assemblies; check the
actual purchased hardware before using them as expansion pins. USB-C uses a
UART bridge. Native S3 USB pins19/20 are already occupied by touch/RGB and
are not a native USB connector in this board profile.

Supplier source and factual references are in bw-parts
[`docs/pin-table-esp32-4848s040.md`](https://github.com/CrispStrobe/bw-parts/blob/d38c65091aca746df8e0cfd00b81097aa5765fb9/docs/pin-table-esp32-4848s040.md).
The vendored JSON/SVG are generated with
`node scripts/sync-parts-data.mjs --dir ../bw-parts --only esp32_4848s040`.
The exact merged supplier is `d38c65091aca746df8e0cfd00b81097aa5765fb9`;
the scoped sync with `--overwrite --check` reports zero JSON/SVG drift.

## Runtime binding

`CircuitDesigner` and `BoardCanvas` accept two optional props:

- `esp32S040PartId`: the id of the single placed board that owns the target.
- `onEsp32S040Input(changes)`: a stable callback forwarding the typed batch
  to the owning target's existing `setInputs(changes)` API.

The owner alone receives the existing `videoFn`; `CircuitDesigner` gets it
from `debugState.video`. Other placed panels remain static with **Display
pending**. Do not infer ownership merely because a project contains a panel
or because an unrelated target can produce video.

The face accepts the existing `target.video()` shape:

```js
{
  width: 480,
  height: 480,
  rgba: Uint8Array, // 480 × 480 × 4 bytes; already decoded by bw-board
  frame: Number,
  signal: Boolean,
  panel: { // optional, supplied only from actual engine metadata
    displayOn: Boolean,
    sleeping: Boolean,
    backlightOn: Boolean,
    powered: Boolean,
    framesReceived: Number
  }
}
```

Wrong dimensions, absent pixels, no signal, power loss, sleeping, display
off, backlight off and a zero frame count cannot retain an earlier bright
frame. Unavailable data stays explicit. The face does not invent a splash
screen, a successful firmware run or an idle blinking program. RGB565 to
RGBA decoding belongs to the target adapter; the UI presents those pixels
without applying another rotation or gamma correction. Firmware can draw
in a software-rotated coordinate space; the UI does not claim hardware
ST7701 MADCTL emulation.

Pointer input uses the inverse SVG screen transformation, including circuit
zoom, part rotation and flipping, to produce sensor coordinates `0…479`.
One pointer owns the current contact. A down sends one atomic batch:

```js
[
  { component: 'touch', channel: 'x', value: x },
  { component: 'touch', channel: 'y', value: y },
  { component: 'touch', channel: 'pressed', value: 1 }
]
```

A captured move sends x/y updates; coordinates outside the screen clamp
to its edge. Up, cancel, lost capture, owner/callback replacement, display
loss and unmount send `pressed: 0` to the callback that received the down.
A second finger cannot replace or release the first. Callbacks should be
stable for one target session, and change when ownership changes. This is
one contact; it does not claim full five-contact GT911 support.

## Qualification boundary

The source tests exercise the actual Circuit model and installed bw-board
package: H1 names, face/hit geometry, refusal of seating/internal pins,
save/load, source voltage domains, declaration inference, and the absence of
synthetic GPIO arming. A board without external PIN declarations is placed
alone; an explicit loaded circuit retains precedence.

`test/esp32-4848s040-face.browser.mjs` exercises actual React components in
Chromium with a labelled **test-supplied frame**. It checks RGBA corners,
rotated/mirrored mouse coordinates, captured drag, real touch contacts,
cancellation/release, owner isolation, blanking and the actual Designer
placement/load paths. It runs after the existing `verify:interaction` suite;
no existing scenario or threshold is removed. `BW_S040_CHROMIUM` optionally
selects a locally installed browser; normal CI uses the pinned Playwright
browser. `BW_S040_SCREENSHOT` optionally writes a review screenshot.

These tests qualify the consumer contract. They do not qualify booting
arbitrary ESP-IDF/Arduino firmware, Wi-Fi/Bluetooth, SD, relays, audio, analog
gamma, physical bus timing or cycle accuracy. The engine, bw-board adapter
and Lite host must be qualified separately before a live firmware target is
advertised. On an older engine the physical part is a static MCU passthrough,
with no inferred internal regulator or peripheral behavior.
